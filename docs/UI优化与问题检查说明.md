# UI 优化与问题检查说明

## 交付范围

本包以本次上传的完整源码为基础，保留 `backend/`、`sql/`、原有设计文档及部署方式。209 个后端文件与 2 个 SQL 文件均与原包字节一致。前端依赖版本、接口地址和已有表单的业务字段保持原有定义；新增测试仅使用模拟接口。

此次修改集中在界面呈现和前端交互缺陷修复，不调整采收休药期、生产入库、销售出库审核、库存扣减、质检、溯源生成等后端业务规则。无需执行数据库迁移。

## 界面优化

- 全局采用深绿、蜂蜜金和浅色背景，统一按钮、状态标签、卡片、表格、表单、分页、提示及弹窗。
- 调整侧栏、页头与内容间距，消除表格卡片重复内边距；补充页面标题和简短业务说明。
- 登录页调整品牌区、表单层次与输入标签，支持浏览器账号自动填充；“记住用户名”仍仅保存用户名。
- 数据看板保留 8 项统计及全部原图表，调整为分组卡片和响应式图表布局；不能访问的快捷入口仍展示数据，但不执行无效跳转。
- 公开溯源页保留产品、采收、蜜源与蜂箱、质检、用药五类信息，优化移动端阅读层次，缺失字段显示占位，失败时显示明确提示。
- 小屏幕采用可展开导航，弹窗限制在视口内，双列表单自动换行，表格保留内部横向滚动。
- 导航与快捷入口使用可聚焦按钮；增加清晰焦点样式与减少动画偏好的支持。

## 已修复问题

| 问题 | 修复结果 |
| --- | --- |
| 列表请求失败后加载状态不结束 | 29 个列表加载函数统一在 `finally` 中释放加载状态；保留已有列表供重试。 |
| 取消删除、审核或退出提示产生未处理异常 | 统一识别确认框的取消/关闭操作，不继续执行请求；重置密码弹窗也可正常取消。 |
| 校验失败或重复点击提交 | 25 处表单校验失败正常返回，30 个保存处理函数增加加载锁；失败保留输入内容。 |
| 弹窗再次打开仍残留校验提示 | 22 个表单弹窗关闭后清理校验。 |
| 切换筛选后仍停留在后面的页码 | 18 个分页查询页面从第一页重新查询；不清除用户输入的筛选条件。 |
| 编辑字典后新增仍沿用旧 ID | 类型与数据的新增对象明确清空 ID，正确使用原新增接口。 |
| 多级相对菜单路径缺少父级 | 逐层拼接导航路径，绝对路径保持原地址；缺失图标使用兼容图标。 |
| 注销后保留上一账号的动态路由 | 注销时移除已注册路由及菜单；身份初始化使用独立标志，空角色列表不会反复初始化。 |
| 旧管理端令牌影响公开溯源 | 公开溯源跳过身份初始化，不附带管理端令牌；登录错误保留接口原提示。 |
| 导出或二维码业务错误被当成文件 | 对 JSON 错误响应显示原提示，不返回为正常下载文件。 |
| 侧栏收缩后图表尺寸不更新、离页后迟到响应创建图表 | 通过容器观察器更新尺寸，统一清理图表；组件卸载后不再初始化图表。 |
| 快速更换报表维度，旧请求覆盖新数据 | 校验请求版本，仅展示最新请求的响应。 |
| 溯源筛选使用错误的批次字段 | 使用后端实际字段 `productBatchId`，恢复原界面已有的“未生成批次”筛选逻辑。 |
| 扫码明细使用创建时间、设备筛选项不完整 | 明细使用 `scanTime`，设备选项与后端输出类型对应。 |
| 二维码对象 URL 未释放 | 替换、关闭预览及离开页面时释放资源；新窗口预览不保留 opener。 |
| 溯源关联数据为空、错误码返回空白页面 | 空关联对象和列表可正常渲染；无效码及接口异常显示明确状态。 |
| 无用药记录被直接描述为“绿色天然” | 改为客观描述“该批次暂无用药记录”，避免把缺少记录当作质量结论。 |

- 原版前端与优化版前端均完成生产构建，最终 `npm run build` 通过。
- 56 项组件和交互回归检查通过：包括 37 个原页面挂载，以及校验、重复提交、失败重试、取消操作、字典新增、查询分页、登录记忆、溯源空状态、二维码清理、路由清理、移动导航、图表生命周期、报表响应顺序和下载错误处理。
- 回归使用 JSDOM、模拟接口和图表替身，未连接实际数据库；图表容器缩放单独验证观察器和销毁行为。这些检查不等同于真实浏览器布局、ECharts 绘制或后端端到端业务验证。

- 构建仍有原项目已有的依赖包体积和 Layout 静态/动态导入提示，不影响构建通过。本轮未更换组件库、升级依赖或改变构建加载策略。

## 代码审查发现、保留待验证的问题

以下根据源码确认存在风险条件，但没有在数据库环境中复现。本轮保留原后端实现，建议下一轮针对性验证。

1. **库存并发与重复审核风险。** `InventoryServiceImpl.stockOp` 和 `OutboundServiceImpl.audit` 使用读取、计算、再写回的流程，没有行锁、版本条件或原子扣减。并发修改同一库存或审核同一单据时，可能出现丢失更新或重复流水。事务本身不能保证这些流程互斥。应在真实 MySQL 环境做并发测试，再采用行锁或条件更新；业务规则可保持原样。
2. **批次号和单号冲突风险。** `HarvestServiceImpl`、`OutboundServiceImpl`、`PurchaseServiceImpl` 通过同日期记录数量加一生成流水号；并发创建会取到相同序号，删除非最后一条记录后也可能再次取到已有序号。数据库唯一索引会阻止重复插入，但用户可能收到保存失败。需要验证并改为可靠的序列分配，同时保留原编号格式。
3. **固定取数上限。** 多处下拉列表取前 100/200 条记录，溯源批次判断和设备统计取前 1000 条。数据超过上限时，可能遗漏可选项或使设备分布仅代表部分记录。建议通过分页完整获取或后端聚合处理；本轮保留现有取数方式和接口。

## 使用与复测

原部署步骤、账号和环境配置请继续参考根目录 README 以及原有部署手册。

```bash
cd frontend
npm ci
npm run dev
```

生产构建：

```bash
npm run build
```

可选的组件回归脚本保存在 `frontend/tests/ui-regression.cjs`。JSDOM 仅用于测试，不加入项目正式依赖，也不修改锁文件：

```bash
npm install --no-save --package-lock=false jsdom@24.1.3
node tests/ui-regression.cjs
```

脚本会在测试目录输出 `regression-results.json`。接口与数据替身只在测试脚本中生效，不进入生产页面。

建议在本地浏览器实际检查登录、侧栏切换、看板图表、查询分页、表单弹窗、二维码和手机溯源页，然后使用原后端与数据库核对完整业务流程。
